# Review Flow Graph Editor + AI Assistant — Design

## 1. Objective

Replace the form-based review flow editor with a **visual canvas editor** in which
a flow is a **decision graph**, and add an **AI assistant** that turns a plain-language
description ("at night use Codex; if Claude is above 80% of its weekly quota, use
Gemini") into a flow draft, generated by one of the agents installed on the machine.

Success criteria:

1. An operator builds or changes any flow by placing and wiring nodes on a canvas —
   no forms-in-a-list.
2. An operator describes a flow (or a change to the current one) in words, picks an
   installed agent, and gets a validated draft painted on the canvas with a short
   plan, which they accept, discard or refine again. Nothing is saved until they
   press Save.
3. A config with no flows keeps choosing the same agents: the built-in `default` flow is still
   built from `primary` / `fallback`.

What the user asked for, verbatim intent: a node editor like the reference screenshot
(palette on the left, canvas in the middle, properties on the right, "Adjust with AI"
button), adapted to Heimdallm; and an assistant where "one of the installed agents
generates the plan and the configuration".

Decisions taken during brainstorming:

| Question | Decision |
|---|---|
| What a flow expresses | A **decision tree/DAG** choosing *who* reviews (not a multi-step review pipeline) |
| Assistant interaction | **Iterative on the canvas**: describe → draft with diff → accept / discard / refine |
| Which agent generates | **Selector** of installed CLI agents, preselected with the daemon's primary agent, last choice remembered |
| Canvas implementation | **Own canvas** (`InteractiveViewer` + positioned node widgets + `CustomPainter` edges), no graph package |

## 2. What exists today and is reused

| Existing | Reused for |
|---|---|
| `config.FlowConfig` / `FlowRule` (`daemon/internal/config/flows.go`) | Replaced by the node-based `FlowConfig` / `FlowNode`; the rule-list format is deleted |
| `config.ScheduleCondition`, `config.QuotaCondition` + their validation | Carried by condition nodes. One change: a schedule with `from == to` is valid and means the whole day (24-hour window on the listed `days`, or every day), so "weekends" is expressible |
| `config.Config.FlowForRepo` (repo > org > global, `legacyFlow`) | Same resolution; `legacyFlow` now builds a graph |
| `flows.Evaluate`, `scheduleHolds`, `quotaHolds` (`daemon/internal/flows/flows.go`) | Condition evaluation reused verbatim; the walk over rules becomes a walk over the graph |
| `exec.Detect` availability check | Same "available" notion while walking agent nodes |
| `RunOptions.Candidates` → `pipeline.selectCLIs` | Untouched: the graph still yields an ordered candidate list |
| `GET/PUT/DELETE /flows`, `POST /flows/simulate`, `GET /quotas` | Same routes, new body shape |
| `agentcatalog.Store` (`GET /cli-agents`) | Installed agents for the assistant selector, the prompt, and the editor dropdowns |
| `executor.Executor.ExecuteRaw` + `StripToJSON` | Running the assistant prompt and extracting its JSON |
| `executor.ValidateWorkDir` | The assistant runs in an empty temp dir under `/tmp` |
| Flutter `ApiClient` flow methods, `PlatformServices`, design system (`mix`) | Editor plumbing and look |

## 3. Data model

### 3.1 TOML

TOML cannot hold slices of nested structs, so nodes are a map keyed by node id
(same reason rules were a map).

```toml
[ai.flows.night-codex]
name  = "Codex at night, Claude while quota lasts"
start = "n1"                       # entry node id; empty = flow has no nodes

[ai.flows.night-codex.nodes.n1]
type  = "condition"
match = "any"                      # all (default) | any
yes   = "n2"                       # edge when the conditions hold; "" = end
no    = "n3"                       # edge when they do not;         "" = end
x = 120.0                          # optional canvas position
y = 80.0
[ai.flows.night-codex.nodes.n1.schedule.s1]
days = ["mon","tue","wed","thu","fri"]
from = "22:00"
to   = "06:00"
tz   = "Europe/Madrid"
[ai.flows.night-codex.nodes.n1.quota.q1]
agent   = "claude"
window  = "weekly"
op      = "above"
percent = 80

[ai.flows.night-codex.nodes.n2]
type  = "agent"
agent = "codex"
next  = "n3"                       # fallback edge: an agent OR a condition; "" = end
x = 360.0
y = 40.0

[ai.flows.night-codex.nodes.n3]
type  = "agent"
agent = "claude"
next  = ""
```

### 3.2 Go types (`daemon/internal/config/flows.go`)

```go
type FlowConfig struct {
    Name  string              `toml:"name"  json:"name"`
    Start string              `toml:"start" json:"start"`
    Nodes map[string]FlowNode `toml:"nodes" json:"nodes"`
}

type FlowNode struct {
    Type     string                       `toml:"type" json:"type"` // "condition" | "agent"
    // condition
    Match    string                       `toml:"match,omitempty"    json:"match,omitempty"`
    Quota    map[string]QuotaCondition    `toml:"quota,omitempty"    json:"quota,omitempty"`
    Schedule map[string]ScheduleCondition `toml:"schedule,omitempty" json:"schedule,omitempty"`
    Yes      string                       `toml:"yes,omitempty"      json:"yes,omitempty"`
    No       string                       `toml:"no,omitempty"       json:"no,omitempty"`
    // agent
    Agent    string                       `toml:"agent,omitempty"    json:"agent,omitempty"`
    Next     string                       `toml:"next,omitempty"     json:"next,omitempty"`
    // layout
    X        *float64                     `toml:"x,omitempty"        json:"x,omitempty"`
    Y        *float64                     `toml:"y,omitempty"        json:"y,omitempty"`
}
```

### 3.3 Validation (`FlowConfig.Validate`, mirrored in Dart)

A flow is rejected when any of these holds; each error carries the offending node id
so the editor can pin it on the node:

- node id not matching `^[a-z0-9][a-z0-9_-]{0,63}$`;
- more than **200 nodes**; existing limits on conditions per node (20) and flows (50) kept;
- `start` non-empty and not an existing node;
- an edge (`yes`, `no`, `next`) pointing at a missing node;
- a **cycle** reachable or not (DFS with colouring over all nodes);
- `type` not `condition`/`agent`; a condition carrying `agent`/`next`, or an agent
  carrying `match`/`yes`/`no`/conditions;
- an agent node with an empty or unsupported agent id (`executor.SupportedCLIs()`);
- condition fields invalid under the existing `ScheduleCondition`/`QuotaCondition` rules;
- a condition node with zero conditions (it would always be "yes"; use an edge instead).

Allowed, flagged as warnings (not errors): nodes unreachable from `start`; agents that
are supported but not installed. Unreachable nodes are ignored by evaluation.

`PUT /flows/{id}` whose body has a `rules` key → `400` ("flows are node graphs; the rules
format is not supported"). The handler checks for the key explicitly before the strict
decode, so the operator gets this message rather than a generic "unknown field".

## 4. Evaluation (`daemon/internal/flows`)

```
walk(start):
  node := start
  for node != "":
    n := nodes[node]
    switch n.Type:
      condition: holds := match(n)            // existing all/any over schedule+quota
                 trace += {node, "condition", holds, reasons}
                 node = holds ? n.Yes : n.No
      agent:     avail := detect(n.Agent)
                 added := avail && !seen[n.Agent]
                 trace += {node, "agent", avail, added}
                 if added { candidates += n.Agent; seen[n.Agent] = true }
                 node = n.Next
```

Termination is guaranteed by validation (acyclic). `Decision` becomes
`{flow_id, flow_name, at, candidates[], path[{node, type, agent?, holds?, available?,
added?, reasons[]}]}` — the `rules[]` field is replaced by `path[]`.

`flowWriteAgents` (merge tracking) walks agent nodes in a deterministic topological
order (Kahn, ties by node id) and keeps write-capable agents without repeats.

## 5. No migration

There is no migration: review flows had no users, and the rule-list format is deleted.
A TOML flow still written with `rules` does **not** fail `Load`: TOML decoding is lenient
and the `rules` keys are ignored as unknown, so the flow loads with no nodes and no
`start`. Validation reports no error for an empty flow, so it loads empty and
`FlowForRepo` silently falls back to the built-in primary/fallback flow. `PUT /flows/{id}`
with a `rules` body is rejected with `400` ("flows are node graphs; the rules format is
not supported"). The synthetic `default` flow from `legacyFlow` (primary → fallback) is
built directly as `a_primary.next = a_fallback`.

## 6. API

| Route | Change |
|---|---|
| `GET /flows` | Body shape follows §3; `agents` becomes `[{id, installed, review_only}]` from `agentcatalog.Store` + `executor.SupportedCLIs()` |
| `PUT /flows/{id}` | Body is a node-based `FlowConfig`; strict decode; validation errors return `422 {errors:[{node, field, message}]}` |
| `DELETE /flows/{id}` | Unchanged |
| `POST /flows/simulate` | `flow` stays the saved flow id; the unsaved graph goes in `graph`: `{flow?, graph?, repo?, at?}`; returns the `Decision` with `path[]` |
| `POST /flows/assist` | **New**, §7 |

The same handlers serve the hub proxy allowlist unchanged (flows are not proxied today).

## 7. The assistant (`POST /flows/assist`)

Request / response:

```json
{ "agent": "claude",
  "instruction": "at night use Codex; if Claude is above 80% weekly, Gemini",
  "flow": { "name": "...", "start": "...", "nodes": { } } }

{ "flow": { }, "plan": "short natural-language explanation",
  "warnings": ["gemini is not installed"], "agent": "claude", "duration_ms": 41230 }
```

`flow` in the request is optional (absent → create from scratch) and may be an
unsaved canvas state.

Steps (`daemon/internal/flows/assist.go`, behind an interface so handlers are tested
with a fake runner):

1. **Guard**: `agent` must be installed per the catalog and not review-only (OpenRouter
   is excluded — `ExecuteRaw` rejects it); else `400`. `instruction` 1–4000 chars.
   One assist at a time per daemon (mutex try-lock) → `409` when busy.
2. **Prompt**: fixed template containing the JSON schema of §3 with the edge semantics,
   the validation rules of §3.3, the installed agents and their models, the quota
   windows each agent currently reports (`GET /quotas` data), the daemon's time zone and
   current time, the current flow JSON (if any) and the instruction inside a fenced,
   clearly delimited block. Output contract: a single JSON object `{plan, flow}`.
3. **Run**: `ExecuteRaw(agent, prompt, opts)` with `WorkDir` = a fresh empty
   `os.MkdirTemp("", "heimdallm-assist-*")` (removed afterwards), no repo checkout,
   the agent run WITHOUT its review permission flags (codex uses the executor's own
   trusted temp workspace instead), a **180 s** timeout for the whole draft including the
   repair round (the response may be held up to 210 s: the write deadline is extended,
   also through the hub proxy), and the request context so a client disconnect kills the
   process group.
4. **Parse & validate**: `StripToJSON` → strict decode → `Validate`. On failure, **one
   repair round**: re-run with the previous output and the validation errors appended.
   Still invalid → `422 {errors, raw_excerpt}` (excerpt capped at 2 KB).
5. **Return** the draft, never persisted. Warnings: unreachable nodes, agents not
   installed, and nodes whose positions are missing (the editor lays them out).

Errors map to: `400` bad request, `409` busy, `422` unusable output, `504` timeout,
`502` agent process failed (with its stderr tail, capped and redacted by the existing
executor redaction).

The instruction is the operator's own text, but it is still fenced and the output is
only ever treated as data: strict decode, full validation, and an explicit accept step
in the UI before anything is saved.

## 8. CLI (`cli/`)

- `heimdallm flows simulate` prints the `path[]` trace (node → decision → reason) and
  the candidate list.
- New `heimdallm flows assist "<instruction>" [--flow <id>] [--agent <id>] [--apply]`:
  prints the plan, warnings and the draft as TOML-ish readable output; `--apply` saves
  it with `PUT /flows/{id}` (requires `--flow`). New `api.Client` methods:
  `AssistFlow`, updated `SimulateFlow` / flow types.

## 9. Flutter editor

### 9.1 Layout (`/flows/:id`)

- **Top bar**: flow name, "Use globally" switch, `Test`, `Undo`/`Redo`
  (Cmd/Ctrl+Z, Shift+Cmd/Ctrl+Z), `Arrange`, `Delete`, `Save` (primary when dirty).
- **Left palette**: "Add step" — **Condition** (schedule / quota) and **Agent**; add by
  double-click on the row (places at viewport centre) or drag onto the canvas. Below it,
  a "How it works" box listing the gestures.
- **Canvas**: dot grid, pan / zoom (`InteractiveViewer`, bounded), fixed **Start** node.
  Condition nodes expose two output ports (**yes**, **no**); agent nodes one
  (**fallback**); every node has one input port. Connect by dragging from an output port
  to a node; dropping on an occupied port replaces that edge. Edges are labelled; hover
  shows a scissors button to cut; a selected node or edge is deleted with
  `Delete`/`Backspace`. A drop that would create a cycle is refused with a toast.
  Unreachable nodes are dimmed with a warning badge; nodes with validation errors get a
  red outline and their message in the inspector.
- **Right inspector**: nothing selected → flow properties (name; where it is used:
  global / orgs / repos, each linking to its screen). Condition → match all/any,
  schedule rows (days chips, from/to, tz) and quota rows (agent, window, op, percent).
  Agent → agent dropdown from `GET /flows` `agents`, not-installed entries labelled.
  At compact width the inspector becomes a bottom sheet.
- **Test**: date-time picker and optional repo; calls `simulate` with the *unsaved*
  graph, highlights the walked path on the canvas and shows the candidate list.
- **Adjust with AI** (floating button, bottom-right): panel with the installed-agent
  selector (primary preselected, last choice remembered via `shared_preferences`) and
  a text box. While running: spinner + Cancel (aborts the HTTP request). The result is
  shown as a **draft overlay**: added nodes green, changed amber, removed shown as red
  ghosts, plus the plan and warnings. **Accept** applies it as one undoable step;
  **Discard** drops it; typing another instruction refines *the draft*. A new flow opens
  with the panel already open.
- Leaving with unsaved changes asks for confirmation (go_router `onExit`).

The `/flows` list stays; "Create" asks for the id, then opens the editor with only the
Start node and the assistant open.

## 10. Testing

- **Daemon** (`make test-docker`): `Validate` (each rule in §3.3); evaluator (branches,
  fallback into a condition, unavailable and duplicate agents, end edges, trace);
  handlers `GET/PUT/simulate` (unsaved graph) and `assist` with a fake runner (valid
  output, repair on second round, `422`, `409`, `504`, `502`, cancellation removes the
  temp dir); `flowWriteAgents`.
- **CLI** (`make test-cli`): simulate trace output; assist with and without `--apply`.
- **Flutter** (`flutter test`, `flutter analyze`, `make build-web`): unit tests for
  `graph_validation`, `auto_layout`, `flow_diff`, controller undo/redo and draft;
  widget tests for add node, connect / cut edge, cycle refusal, inspector edits,
  Test path highlight, AI draft accept / discard / refine, unsaved-changes guard.
- Coverage ratchet must not drop.
- **Local E2E**: a daemon built from the branch with a **hard stop** (unauthenticated
  review agent) so it never reviews real PRs; load a copy of a real config with flows,
  check that `simulate` returns the path the graph predicts for a set of instants; generate a flow with the assistant using a real installed agent and
  save it from the UI.
